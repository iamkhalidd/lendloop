# LendLoop

A tool-lending app for a neighbourhood: people list tools, neighbours request to borrow them, owners approve or decline, and n8n handles notifications and overdue reminders.

**Stack:** Next.js 16 (App Router), Convex, Clerk, n8n, Tailwind.

## What's in it

| Area | Where |
| --- | --- |
| Public landing page: available tool names and categories only | `src/app/page.tsx`, `tools.listPublic` |
| Browse and request tools (signed-in users) | `src/app/(app)/tools` |
| Manage your own listings | `src/app/(app)/listings` |
| Your requests and loans, with automation activity | `src/app/(app)/requests` |
| Incoming requests: approve, decline, mark returned | `src/app/(app)/incoming` |
| Admin: all loans, all listings, members, Trusted Lender flag, automation failures | `src/app/(app)/admin` |
| Data model | `convex/schema.ts` |
| Business rules | `convex/tools.ts`, `convex/requests.ts`, `convex/users.ts` |
| Convex → n8n notifications (signed, with retries) | `convex/notifications.ts` |
| n8n → Convex endpoints (signed, idempotent) | `convex/http.ts`, `convex/automation.ts` |
| n8n workflows (importable JSON) | `n8n/*.json`, generated by `n8n/build-workflows.mjs` |

## Setup

### 1. Install

```bash
npm install
```

### 2. Clerk

1. Create an application at dashboard.clerk.com.
2. Copy the publishable key and secret key into `.env.local` (see `.env.example`).
3. Open **Integrations → Convex** and enable it. This creates the `convex` JWT template. Copy the **Frontend API URL**; it is the issuer domain.

### 3. Convex

```bash
npx convex dev
```

This creates a deployment and writes `CONVEX_DEPLOYMENT` and `NEXT_PUBLIC_CONVEX_URL` to `.env.local`. Then set the deployment's env vars:

```bash
npx convex env set CLERK_JWT_ISSUER_DOMAIN https://<your-app>.clerk.accounts.dev
npx convex env set N8N_NOTIFY_WEBHOOK_URL https://<your-n8n-host>/webhook/lendloop-notify
npx convex env set CONVEX_TO_N8N_SECRET <random hex>
npx convex env set N8N_TO_CONVEX_SECRET <a different random hex>
```

Generate the secrets with `openssl rand -hex 32`. There is one secret per direction, so leaking one doesn't let anyone forge calls the other way.

### 4. Run the app

```bash
npm run dev
```

Sign in once, then make yourself an admin. There is no way to become admin from the UI:

```bash
npx convex run users:setRole '{"email":"you@example.com","role":"admin"}'
```

### 5. n8n

```bash
cp .env.example .env    # fill CONVEX_SITE_URL (ends in .convex.site) and the same two secrets
docker compose up -d
docker compose exec n8n n8n import:workflow --separate --input=/workflows
```

Open http://localhost:5678 and activate the three workflows. A Convex cloud deployment can't reach `localhost`, so for notifications either point `N8N_NOTIFY_WEBHOOK_URL` at a tunnel (ngrok, cloudflared) or use a hosted n8n.

The Code nodes need `NODE_FUNCTION_ALLOW_BUILTIN=crypto` and `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`. `docker-compose.yml` sets both.

## Architecture

```
Browser ──Clerk JWT──▶ Convex queries/mutations (all rules enforced here)
                            │ scheduler (after commit)
                            ▼
              notifications.send ──HMAC POST──▶ n8n "request notifications"
                                                   │ verify → 202 → notify (mock)
                            ◀──HMAC POST /n8n/notification-status──┘

n8n "overdue reminders" (cron 08:00 UTC)
   ──HMAC GET /n8n/overdue-loans──▶ Convex
   ◀── loans not yet reminded today
   remind each (mock) ──HMAC POST /n8n/reminder-status──▶ Convex

n8n "error handler" (errorWorkflow of both) ──HMAC POST /n8n/workflow-error──▶ Convex
```

### Rules, and where they're enforced

Every rule lives in a Convex function. The UI only hides buttons; it never decides anything.

- **Identity** comes from the verified Clerk token (`ctx.auth`). Client-supplied user IDs are never trusted. New users always get the `user` role.
- **Listings:** only the owner can edit. The owner or an admin can remove one, and removing it closes the tool's open requests.
- **Requests:**
  - You can't borrow your own tool.
  - Start date can't be in the past, end date ≥ start date, and a loan lasts at most 30 days.
  - One open request per tool per borrower.
  - A request can't overlap an approved loan.
- **Decisions:** only the tool's owner can decide, and only while the request is pending. Approving a request declines any overlapping pending requests and gives a reason.
- **Returns:** the owner or an admin marks a loan returned, and only once it has started.
- **Not yours = not found.** Asking for someone else's record gives the same error as asking for one that doesn't exist, so IDs can't be probed.
- **Admin-only:** `listAll`, `listForAdmin`, `setTrustedLender` and `recentFailures` all call `requireAdmin` on the server.

### Data minimisation

- **Signed-out visitors** see tool name and category only. No owner, no description.
- **Signed-in users** see owners' first names only, never emails.
- **Notifications to n8n** carry the recipient's name and email, the other party's first name, the tool name, dates and an optional reason. Nothing else.
- **The overdue feed** carries only what one reminder needs.
- **Write-backs** carry IDs, status and channel. No personal data goes back.
- **The error workflow** sends the error message only: no stack trace, no node input data.
- Email is stored only so notifications can be sent.

### Webhook security

- **What's signed:** `HMAC-SHA256(secret, "${timestamp}.${METHOD}.${path}.${rawBody}")`. It's sent as `X-LendLoop-Timestamp` and `X-LendLoop-Signature`.
- The signature covers the method and path, so a valid signature for one endpoint can't be replayed on another.
- Timestamps more than 5 minutes off are rejected.
- Signatures are compared in constant time.
- If a secret isn't configured, the request is rejected (fail closed).
- Every failure gets the same 401, with no reason given.
- Signatures are checked over the exact raw bytes received, before JSON is parsed. Bodies are capped at 16 KB.

### Reliability and idempotency

- Notifications are scheduled **after** the mutation commits. A rolled-back transaction never sends one.
- Convex retries a failed delivery with exponential backoff: 10s, 20s, 40s, 80s, so 5 attempts in total. After that it records `notification_failed`, which shows in the admin view and on the loan.
- n8n's HTTP nodes retry 3 times, 3 seconds apart.
- Every write-back has a natural key:
  - `reminder_sent:<loanId>:<date>`
  - `notification_sent:<requestId>:<event>`
  - `workflow_error:<executionId>`

  The key is checked and the row inserted inside one serializable Convex mutation. A retried write-back returns `duplicate: true` and stores nothing new.
- The overdue feed skips loans that already have today's reminder, so re-running the workflow the same day sends nothing twice.

## Tests

```bash
npm test
```

**`convex/rules.test.ts`** uses `convex-test` against the real schema and functions. It covers:
- what the public list exposes
- that signed-out users are blocked
- that non-owners can't edit or remove listings, and admins can remove them
- that you can't borrow your own tool
- that only the owner can approve
- that approving declines overlapping requests
- date validation
- who can mark a loan returned
- that admin-only functions reject normal users
- that signing in doesn't make you admin
- that unsigned or wrongly signed n8n calls get a 401
- that a signature can't be replayed on another path
- what the overdue feed contains
- reminder idempotency, including the same-day re-run and the activity line the borrower sees

**`n8n/workflows.test.ts`** runs the Code-node source from the exported workflow JSON, with small stand-ins for n8n's globals. It checks that:
- n8n accepts what Convex signs, and rejects tampered, wrong-secret and stale requests
- Convex accepts every request n8n signs
- write-backs carry no personal data

## Production notes

- **Real notifications:** swap the two "(mock)" Code nodes for Send Email / Slack nodes, and keep their output shape so the write-back still works.
- **Duplicate notifications:** Convex retries if n8n never answered, so a notification can, rarely, go out twice. To prevent that, add an n8n "Remove Duplicates" step keyed on `eventId` (across executions) before sending.
- **Rate limits:** add rate limiting on request creation (for example `@convex-dev/rate-limiter`).
- **Ledger retention:** prune `automationEvents` older than about 90 days with a Convex cron.
- **Version pinning:** pin the n8n image version instead of `latest`.
- **Secret rotation:** to rotate secrets without downtime, accept two secrets during the overlap.
- **Time zones:** "today" is UTC throughout. A real neighbourhood app would store a time zone per community.
- **Larger catalogues:** `listPublic` and `list` read up to a fixed number of rows. A large catalogue would need pagination.
